# POPIN LMS

School operations workspace built with Next.js, React, Prisma, and PostgreSQL.

## Stack

- Next.js 15
- React 18
- TypeScript
- Tailwind CSS
- Prisma
- PostgreSQL 16 hosted in Docker

## Local Development

```bash
cp .env.example .env
npm install
npm run db:up
npm run db:migrate
npm run db:seed
npm run dev
```

On Windows PowerShell, use `Copy-Item .env.example .env` instead of `cp`.
Docker Desktop must be running with Linux containers. Set `AUTH_SECRET` in `.env`
to a random secret, for example one generated by
`node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`.
Seeding creates demo users; it is optional when starting with an empty database.

Open:

```text
http://127.0.0.1:3000
```

## Environment Variables

The web app requires these values in production:

```text
DATABASE_URL=postgresql://popin:YOUR_PASSWORD@YOUR_DATABASE_HOST:5432/popin_lms?schema=public
AUTH_SECRET=...
NEXT_PUBLIC_AUTH_BYPASS=false
NEXT_PUBLIC_APP_URL=https://your-domain.vercel.app
APP_URL=https://your-domain.vercel.app
```

`NEXT_PUBLIC_AUTH_BYPASS` is optional and should stay `false` in production.

## Database

### Local PostgreSQL with Docker

The root [docker-compose.yml](docker-compose.yml) is the default database setup.
Next.js and Prisma running on your computer connect to `localhost:5432` using
the `DATABASE_URL` in `.env`. Compose reads the same `.env` for `POSTGRES_DB`,
`POSTGRES_USER`, `POSTGRES_PASSWORD`, and `POSTGRES_PORT`.
Keep the URL and these settings in sync, including the port. URL-encode special
characters in credentials used in `DATABASE_URL`.

Start the database and wait until it is healthy:

```bash
npm run db:up
```

Apply migrations and optionally seed demo users:

```bash
npm run db:migrate
npm run db:seed
```

Data persists in the `popin_lms_postgres_data` volume when the container stops or
is recreated. `npm run db:down` stops the database without deleting data;
`npm run db:logs` shows its logs. The database port is bound to localhost.
PostgreSQL initialization variables apply only to a new data volume; changing
them in `.env` does not change an existing database's credentials.

The alternative files under `infra/` use the same defaults but retain their
existing `popin_pg` volume. Run only one local PostgreSQL stack at a time.
When using those files, pass `--env-file .env` from the repository root.

Generate Prisma client:

```bash
npm run db:generate
```

Apply migrations:

```bash
npm run db:migrate
```

Seed demo data:

```bash
npm run db:seed
```

### Docker production hosting

The production stack runs PostgreSQL, a migration job, the Next.js app, and
Nginx. Configure `.env` with a strong `POSTGRES_PASSWORD`, a random `AUTH_SECRET`,
and your public `APP_URL` and `NEXT_PUBLIC_APP_URL`. Use a URL-safe password
(for example a generated hexadecimal secret), because the stack constructs
the container's database URL from `POSTGRES_USER`, `POSTGRES_PASSWORD`, and
`POSTGRES_DB`. Host-run Prisma commands still need a matching `DATABASE_URL`.

```bash
docker compose --env-file .env -f infra/docker-compose.prod.yml up -d --build
```

The app connects to `postgres:5432` inside Docker. PostgreSQL has no published
host port in this stack. The app starts after PostgreSQL is healthy and the
migration job succeeds. Nginx serves the app and its `/api` routes on port 80;
configure HTTPS at your hosting reverse proxy. Public Next.js settings are
included during the image build, so rebuild after changing them.
Production data persists in the `popin_pg` volume; keep regular database backups.

To run migrations separately or intentionally seed this deployment:

```bash
docker compose --env-file .env -f infra/docker-compose.prod.yml run --rm migrate
docker compose --env-file .env -f infra/docker-compose.prod.yml run --rm migrate npm run db:seed
```

## Vercel Deployment

This repo is ready to deploy to Vercel.

If the app is hosted on Vercel, `DATABASE_URL` must point to a reachable address
for your Docker-hosted PostgreSQL server, with the server's required TLS settings.
`localhost` and Docker service names are only valid on the database host or its
Docker network; they cannot be used by Vercel. Restrict remote database access
to your hosting network.

Use these project settings:

- Root Directory: `.`
- Framework Preset: `Next.js`
- Install Command: `npm install`
- Build Command: configured in `vercel.json`. Production deployments apply
  `npm run db:migrate` before `npm run build`; preview deployments only build.

Set these environment variables in Vercel:

- `DATABASE_URL`
- `AUTH_SECRET`
- `NEXT_PUBLIC_AUTH_BYPASS=false`
- `NEXT_PUBLIC_APP_URL`
- `APP_URL`
- `JOBS_SECRET` (a unique random value of at least 24 characters)
- `CRON_SECRET` (a different unique random value of at least 24 characters)

If you are enabling live integrations, also set:

- `RESEND_API_KEY`
- `RESEND_FROM_EMAIL`
- `RESEND_FROM`
- `TWILIO_ACCOUNT_SID`
- `TWILIO_AUTH_TOKEN`
- `TWILIO_FROM_NUMBER`
- `TWILIO_MESSAGING_SERVICE_SID`
- `TWILIO_WHATSAPP_FROM`
- `NEXT_PUBLIC_PAYSTACK_PUBLIC_KEY`
- `PAYSTACK_SECRET_KEY`

Notes:

- Prisma client generation is automated during `postinstall`, which is Vercel-safe.
- Production Vercel deployments run `npm run db:migrate` before the build. The
  migration command is safe to rerun because Prisma records applied migrations.
- The Vercel Cron configuration calls `/api/jobs/run` hourly in production to
  dispatch scheduled communications, process queued assessment work, and clear
  expired security records. Vercel supplies `CRON_SECRET` as its bearer token;
  do not use the local Docker worker in Vercel.
- To deploy automatically from GitHub pushes, configure the `production`
  environment secrets `VERCEL_TOKEN`, `VERCEL_ORG_ID`, and
  `VERCEL_PROJECT_ID`. The `Deploy Vercel Production` workflow deploys every
  push to `main`.
- Run `npm run db:seed` only if you intentionally want seeded records in that environment.
- Set the Paystack callback to `https://your-domain.vercel.app/parent-portal/payment-callback` or a custom domain equivalent.
- Set the Twilio status callback to `https://your-domain.vercel.app/api/webhooks/twilio/status`.
- Set the Paystack webhook to `https://your-domain.vercel.app/api/webhooks/paystack`.

## Operational setup and completed workflows

The active setup uses email/password authentication and manual script review. External identity and OCR remain disabled unless deliberately configured later. Staff MFA uses emailed, expiring one-use codes when enabled in Authentication settings; Resend must be configured first. Password recovery also requires Resend. Browser sessions use HttpOnly cookies, have server-side revocation and idle expiry, and require same-origin writes.

Portal and inventory collections are persisted as individual `DataRecord` rows, with dedicated tables for store orders, documents, suppliers, sessions and authentication challenges. Existing JSON records remain readable until converted. API writes use PostgreSQL transactions and a shared advisory lock; readers use consistent snapshots. This intentionally serializes legacy workflows for correctness. Attachments are validated PDF/PNG/JPEG binaries in PostgreSQL, included in database backups and downloadable only by owners or administrators.

After backing up an existing installation, run `npm run db:migrate` and `npm run db:migrate-records`. The second command converts existing records and eligible legacy orders in one transaction. Keep the backup until the migrated installation has been verified. Never reseed an installation containing real school data.

New store orders appear in both Store order history and the owning parent's portal. Staff verify an EFT reference or receive a validated Paystack webhook, prepare the order, and mark it ready; the parent can then collect it. Refund recording requires the reference of a refund already completed with the bank/provider. Cancelling an unpaid order or recording a refund restores stock once. Unsupported PayFast/Ozow choices have been removed.

### Local background processing and backups

Set a random `JOBS_SECRET` of at least 24 characters in `.env`, then run:

```powershell
docker compose --profile processing up -d
```

The worker calls the local app on port 3000 using Docker Desktop's `host.docker.internal`. It dispatches due campaigns, retries failed deliveries with backoff, records terminal failures, and skips recipients already logged as delivered. External providers can still produce an uncertain delivery result after a timeout; inspect provider logs before manually repeating a failed campaign. App open counts are not estimated from delivery counts.

Daily PostgreSQL custom-format dumps are saved to `infra/backups`, retained for 14 days and excluded from Git and Docker images. Copy encrypted backups to an off-host destination as part of your hosting setup. A local disk backup does not protect against loss of the host.

To verify a dump, copy it into the database container and execute `infra/restore-check.sh` there with `POSTGRES_USER` set and the dump path supplied. It restores into the dedicated `popin_restore_test` database, checks the tables, and removes only that disposable database. Never restore over the live database as a test.

### Production release

`infra/docker-compose.prod.yml` includes PostgreSQL, migration, web, worker, backup, monitoring, and a Caddy HTTPS proxy. Set `PUBLIC_HOST` to the public DNS name and `NEXT_PUBLIC_APP_URL` to its HTTPS URL; point DNS to the host and open ports 80/443. Set strong database, authentication and worker secrets. Preserve `ENCRYPTION_KEY` when rotating `AUTH_SECRET` if optional identity credentials have been encrypted.

The manual GitHub Release workflow runs checks, publishes an immutable `sha-<commit>` image to GHCR and deploys through SSH. Configure the `production` environment with `PUBLIC_APP_URL`, plus secrets `DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_KEY` and `DEPLOY_KNOWN_HOSTS`. The host needs a checkout at `/srv/popin-lms`, its private `.env`, Docker Compose, and permission to pull the GHCR image. Host key verification is mandatory. The deployment script backs up PostgreSQL, applies migrations and checks service health. On failed startup it attempts to restore the previous application image; database changes remain and must be backward compatible.

Monitoring records health failures and can notify an `ALERT_WEBHOOK_URL` after three consecutive failures. The backup service has its own freshness health check. Configure external uptime monitoring and an off-host backup destination before launch. Actual HTTPS issuance, SSH deployment and provider acceptance require the real domain, host and credentials and cannot be validated against the local development environment.

### Regression checks

Set `DATABASE_URL` to a disposable database whose name ends in `_test`, with the migrations applied, plus test-only `AUTH_SECRET` and `JOBS_SECRET`. Run `npm run test:integration`. The runner clears that database, starts an isolated Next.js server and tests permissions, parent/teacher workflows, notification routing, concurrent writes and checkout, documents, scheduled delivery, manual marking, supplier records and authentication. CI runs these checks before building.

Optional adapters follow the [Microsoft OIDC protocol](https://learn.microsoft.com/en-us/entra/identity-platform/v2-protocols-oidc), [Google OIDC protocol](https://developers.google.com/identity/openid-connect/openid-connect), and [Tesseract documentation](https://tesseract-ocr.github.io/tessdoc/). They remain inactive in the current manual setup. Marketing connection checks make real HTTPS requests only to hostnames explicitly listed in `MARKETING_ALLOWED_HOSTS`; the status view reports stored results rather than simulated success.
